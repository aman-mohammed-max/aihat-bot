# Development status

## Current phase

Phase 9 — production readiness verification. The Bun and Cloudflare runtimes, shared agent core, factory, Telegram/Mini App/Web Chat interfaces, skills/MCP, scheduling, tenant security, and runtime-parity coverage are implemented and the development Worker is deployed. Remaining production gates are external configuration: a public HTTPS malware-scanner gateway and secret, the optional BotFather browser Login Client ID, and approved staging/production Cloudflare resources and secrets. Arbitrary-code sandboxing remains explicitly unsupported; no unsafe in-process execution is enabled.

Telegram's send API cannot deduplicate outbound notifications, so a crash after Telegram accepts a message but before D1 records completion can produce a duplicate; automatic retries and owner-requested recovery are at-least-once.
- Encrypted-secret operations require deployment-injected keyrings. Bun secret rotation is available through `bun run rotate-secrets:bun`; Cloudflare D1 rotation uses `bun run rotate-secrets:cloudflare` with the operator-only Worker secret configured. Both object stores provide bounded streaming and buffered methods up to 25 MiB; Telegram attachment handling still buffers its smaller, explicitly bounded files.
- MCP supports encrypted static bearer credentials, OAuth client-credentials, and OAuth authorization-code user consent with PKCE over Streamable HTTP. Unhealthy servers retry on later agent requests with a persistent lease, exponential backoff capped at 15 minutes, and at most five attempts. SSE-only transports, background reconnect scheduling, and permissions beyond the explicit `mcp:invoke` grant are unavailable.
- Image providers must return an HTTPS URL; inline-base64-only image output cannot yet be delivered. Generated provider URLs are shown in the immediate response but are not retained in conversation history. Persistent files are private to bot owners and cannot be downloaded until scanning is clean.
- Workflow execution is available for installed catalog entries, with up to 32 forward-only steps and 60 KiB encrypted checkpoints that expire after 30 days and are purged on a later workflow invocation. Owner-published workflow definitions are validated against enabled catalog children. Custom-code sandbox execution remains unsupported.
- Successful non-workflow tool results are encrypted and replayed for seven days by the shared tool registry. Expired results are purged opportunistically on a later tool call from the same tenant. External effects remain at-least-once when a process stops after the remote action succeeds but before the result commit; ambiguous outcomes use owner-reviewed recovery.
- Telegram accepts text, bounded JPEG/PNG/WebP photos, UTF-8 TXT/Markdown/CSV/TSV/JSON/JSONL/XML/YAML/log documents up to 64 KiB, and scanned PDF/DOCX documents up to 2 MiB. PDF text extraction supports at most 20 pages; scanned PDFs need OCR. DOCX extraction reads only the main document XML, with a 1 MiB expanded XML limit. Image analysis is disabled unless the operator enables it for a vision-capable model. Only owner-approved sender IDs can invoke the agent, and each sender needs an explicit grant for every installed skill or enabled MCP tool in addition to the bot-level grant.
- Customer Telegram bot tokens are submitted over HTTPS through the owner-scoped management API and encrypted at rest. `TELEGRAM_MASTER_BOT_TOKEN` (or legacy `TELEGRAME_BOT_TOKEN`) is used for Mini App identity verification and master-bot API calls; the master webhook separately requires `TELEGRAM_MASTER_WEBHOOK_SECRET`. `TELEGRAM_BOT_TOKEN` is not consumed.
- Public/shared access has per-user quotas and revocable grants, authenticated API requests have account-wide and network-wide limits, and Telegram master-bot private chats and approved customer-bot senders have persistent per-user limits. API writes, scope/resource denials, bot access outcomes, membership/invitation changes, skill/MCP permission checks, and factory/credential approval outcomes are audited. Workspace invitations grant membership only; they do not grant access to private bots. Bun's network limiter observes the socket peer address; deployments behind reverse proxies must enforce a corresponding ingress limit. This repository is not production-ready.
