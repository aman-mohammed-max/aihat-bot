# AI Hat Bot Factory

An extensible platform for creating and hosting AI bots across self-hosted Bun and Cloudflare Workers runtimes. The shared TypeScript core contains the agent loop, provider contract, tool permissions, bot creation state machine, encryption contract, and runtime ports.

## Current implementation

- `packages/core`: shared domain types, errors, provider/agent interfaces, agent orchestration, tool permissions, bot factory, encryption and rotation, scheduling, and buffered/streaming object-storage ports.
- `apps/bun-runtime`: Bun HTTP API, SQLite repositories and migrations, AES keyring, private file object storage, and an optional ClamAV daemon adapter.
- `apps/cloudflare-runtime`: Worker API, D1 repositories, SQLite-backed Durable Object alarms, Queue producer, and tenant-prefixed R2 object storage.
- `migrations/sqlite`: forward-only tenant-aware schema migrations for bots, sessions, approvals, credentials, Telegram deployments, conversations, skills/MCP, scheduled tasks, jobs, audit records, access grants, uploaded-file metadata, ambiguous tool-call recovery, recipient-approved ownership transfers, and explicit bot collaborators.

Both runtimes expose `GET /health`, `GET /ready`, and `GET /capabilities`, shared API-token identity and management endpoints, tenant member administration, the authenticated bot-creation API with provider-backed chat, image, and search model selection, bot lifecycle routes, skill and MCP management routes, owner-scoped agent, conversation-history, memory, and usage endpoints, public bot discovery, private direct-user grants, explicit viewer/editor bot collaboration, and shared/invitation access, Telegram webhooks with photo and structured text-file input, scheduled task management, and the responsive dashboard at `/miniapp/`. Published public bots that enable the `web_chat` interface have a shareable chat page at `/chat/{slug}`; visitors sign in with Telegram or an API token, and requests use the existing per-user quotas and rate limits. Bots can be listed, edited with optimistic version checks, disabled/enabled, and deleted. Collaborators are named active workspace members; viewers can read bot identity and editors can update its name, description, and system prompt, while credentials and operational controls remain with the owner. The factory supports pause/resume, draft creation, publishing, encrypted model credential connection, and short-lived one-use approvals for credential connection, public visibility, and publication. Tokens and approvals are stored only as SHA-256 hashes; issued tokens and approvals are shown once. Prompt, HTTPS, forward-only workflow, and MCP Streamable HTTP tools are supported. Workflow definitions must come from trusted catalog records and call installed HTTP or registered idempotent native skills. HTTP and MCP calls require exact operator allowlisting through `HTTP_SKILL_ALLOWED_ORIGINS` and `MCP_ALLOWED_ORIGINS`; discovered MCP tools remain disabled until explicitly granted. MCP supports encrypted bearer credentials, OAuth client credentials, and OAuth authorization-code consent with PKCE. The OAuth callback is fixed to the same-origin `/miniapp/` URL, and each discovered tool still requires an explicit grant. A multi-stage Bun Docker image and Compose setup are available for self-hosting. Telegram Mini App sign-in is available when the master bot token is configured; streaming and strict structured output are enabled only for origins the operator explicitly verifies. Audio/video attachment handling remains unfinished. Telegram users must be explicitly allowlisted and receive per-user grants for each installed skill or enabled MCP tool. Do not connect owner-sensitive tools or use this build with real customer data.

Factory setup also offers `POST /v1/factory-assist/generate`, using `FACTORY_LLM_ENDPOINT`, `FACTORY_LLM_MODEL`, and `FACTORY_LLM_TOKEN` to draft the creative bot profile for owner review. When these settings are present, Telegram users can send `/create <idea>` to prefill the same creative fields before selecting providers, credentials, permissions, and publishing choices.

Each bot has private uploaded-file storage managed from its Files tab. List files with `GET /v1/bots/{botId}/files`; upload a raw request body with `POST` to that route, setting `Content-Type` and the percent-encoded `x-file-name-encoded` header. `GET /{fileId}` reads metadata, `POST /{fileId}/scan` retries a failed scan, `GET /{fileId}/content` downloads a clean file, and `DELETE /{fileId}` removes it. The API accepts JPEG, PNG, WebP, PDF, plain text, Markdown, CSV, TSV, JSON, JSONL, XML, YAML, and log files up to 25 MiB each, 100 files and 250 MiB per bot. File bytes use the runtime object store (R2 in Cloudflare); D1/SQLite stores owner-scoped metadata. Only files marked clean can be downloaded. Bun can scan through a private ClamAV daemon; Cloudflare requires an operator-managed HTTPS scanner gateway. Without a scanner, new files remain quarantined and Telegram attachments are refused. See the scanner configuration and request contract in [the Cloudflare runtime guide](apps/cloudflare-runtime/README.md#file-scanning).

Remote tool calls with expired leases or failed result storage appear in the bot's Tool recovery tab. Owners can inspect the external service, then approve one retry or close the call. Approval permits replay of the original request with its existing idempotency key; it does not send a new request from the dashboard. A retry can still duplicate an action if the remote service accepted the first attempt.

The runtimes register reviewed native TypeScript handlers from application code; migration `0027_native_text_statistics.sql` adds the built-in `aihat.text.statistics.v1` skill to the shared catalog. Bot owners install it and grant `text:analyze` before the model can call it. Global catalog publication accepts native metadata only when it exactly matches a code-registered handler; arbitrary tenant code and sandbox execution remain disabled.

The model adapter retries non-streaming requests on bounded transient HTTP statuses. Configure `MODEL_RETRY_MAX_ATTEMPTS` (1–3, default 2) and `MODEL_RETRY_BACKOFF_MS` (0–3000 ms, default 250) in the runtime environment. The adapter caps `Retry-After` at three seconds and does not retry streaming or ambiguous network failures. Telegram retries only explicit `429` responses and can be limited with `TELEGRAM_RETRY_MAX_ATTEMPTS` (1–3) and `TELEGRAM_RETRY_MAX_AFTER_SECONDS` (0–3). Master-bot private chats use a persistent per-user limit of 30 requests per minute by default; configure `TELEGRAM_MASTER_REQUESTS_PER_MINUTE` from 1 to 1,000. Dynamic HTTP/API and login routes also share a persistent per-network limit across accounts, defaulting to 600 requests per minute; configure `NETWORK_REQUESTS_PER_MINUTE` from 10 to 10,000. Only a keyed hash of the client address is stored. Bun uses the socket peer address and does not trust forwarded headers; deployments behind reverse proxies should apply a corresponding ingress limit there. Telegram webhooks are authenticated and use their separate sender limits. Scheduled jobs use `SCHEDULED_TASK_RETRY_MAX_ATTEMPTS` (1–10), `SCHEDULED_TASK_RETRY_BACKOFF_MS`, and `SCHEDULED_TASK_RETRY_MAX_BACKOFF_MS` (both capped at one hour). Model, HTTP-skill, Telegram, and scheduled-job retries emit sanitized structured events; no request body or credential is logged. A provider may still charge for a request that returned a transient server error.

Factory routes include `POST /v1/factory-sessions`, `GET /v1/factory-sessions/{sessionId}`, and `POST` actions at `/{sessionId}/pause`, `/resume`, `/answer`, `/credentials`, `/models`, `/draft`, `/publish`, and `/approvals`. Session reads require `factory:read`; changes require `factory:write`. Connect a model credential using an `approvalId` from `/approvals`; the encrypted credential response contains only its opaque reference. The `/models` action fetches the endpoint's OpenAI-compatible `/models` listing for the active role. Model discovery uses exact HTTPS origins in `MODEL_ALLOWED_ORIGINS`; temporary chat credentials are not saved in factory-session answers. At runtime, selected image and search models enable `generate_image` and `search_web` tools that call `/images/generations` and `/search` on the same approved provider endpoint. Image results with HTTPS URLs are returned as attachments to the API and Mini App preview, and are sent as Telegram photos. Telegram's retry record stores the image URL only in the encrypted secret store. Providers returning only inline base64 receive an explicit unsupported-capability response.

Send messages to `POST /v1/bots/{botId}/messages` with the `agent:run` scope. Bot ownership and conversation history are scoped to the authenticated token owner. Send a stable `Idempotency-Key` header when retrying the same request; requests without one receive a fresh execution identity. Model requests are allowed only to HTTPS origins listed in `MODEL_ALLOWED_ORIGINS`. To receive Server-Sent Events, send `{ "message": "…", "stream": true }` with `Accept: text/event-stream`. `delta`, `done`, and `error` events carry incremental text, the final reply, and sanitized failures. Streaming requires the endpoint origin to appear in both `MODEL_ALLOWED_ORIGINS` and `MODEL_STREAMING_ORIGINS`; custom compatible endpoints remain non-streaming until the operator verifies their SSE behavior.

Successful tool calls are now checkpointed in a tenant- and bot-scoped ledger. Bun SQLite and D1 store only the lease, input fingerprint, and encrypted result reference; tool results and generated-image URLs remain in the encrypted secret store and replay for seven days. Concurrent retries wait on the existing lease, and reusing a request identity with different tool input fails with a conflict. A failed call releases its lease for retry. External effects still have at-least-once behavior if the remote service completes an action and the Worker or process stops before the encrypted result is committed; this ledger does not claim exactly-once delivery.

For a strict non-streaming JSON response, include a bounded JSON Schema object in `responseSchema`; the response contains both a JSON-string `message` and parsed `structuredOutput`. The supported schema subset covers nested objects, arrays, primitive types, and primitive enums, with all object properties required and `additionalProperties: false`. Schemas are limited to 12 KB and 500 nodes; structured provider output is limited to 64 KB. Structured output is rejected for streaming calls and unless the model endpoint origin appears in both `MODEL_ALLOWED_ORIGINS` and `MODEL_STRUCTURED_OUTPUT_ORIGINS`. Add an origin to the latter only after verifying that the configured endpoint honors OpenAI-compatible strict `json_schema` responses. `GET /capabilities` reports `modelStructuredOutput` when the configured origin sets overlap.

Read owner-scoped history with `GET /v1/bots/{botId}/conversations` and `GET /v1/bots/{botId}/conversations/{conversationId}/messages` (`bots:read`). Read the last 1–90 days of successful requests, provider-reported token totals, and model retry counts by bot, date, and HTTP status with `GET /v1/usage?days=30` (`bots:read`). Analytics omit actor identifiers, prompts, and message content; token counts are zero for providers that do not return usage metadata.

Review recent authenticated API write attempts and factory approval outcomes with `GET /v1/audit-logs?limit=50` (`bots:read`). The audit log stores the method and path, but never request bodies, query strings, approval IDs, or hashes. Agent message requests are excluded from mutation history.

Manage workspace accounts with `GET` and `POST /v1/members`, `PATCH /v1/members/{userId}`, and `DELETE /v1/members/{userId}` (`members:manage`). Owners can add an existing account as an admin or member, change active member roles, and deactivate accounts; admins can list members, but only owners can mutate membership. Owners can create one-use, expiring workspace invitations with `POST /v1/invitations`, list them with `GET /v1/invitations`, and revoke pending invitations with `DELETE /v1/invitations/{invitationId}`. Signed-in accounts accept a token with `POST /v1/invitations/accept`; the dashboard can accept an invite link automatically or a token pasted after sign-in. Invitation tokens are stored only as hashes and returned once. Deactivation preserves owned data, revokes that user's active workspace API tokens, and prevents reactivation from reviving those tokens. Private bots still require explicit per-bot access grants. Membership mutations are recorded in the workspace audit log.

An account with more than one active membership can use `GET /v1/workspaces` to list workspaces and `POST /v1/workspaces/switch` with `{ "tenantId": "..." }` to exchange its session for a workspace-scoped token. Effective scopes are limited by both the source token and the user's role in the selected workspace; the exchanged token expires no later than the source token or 12 hours. Workspace switching does not grant access to another member's private bots.

Manage a bot’s owner-authored long-term notes with `GET`, `PUT /v1/bots/{botId}/memory/{key}`, and `DELETE /v1/bots/{botId}/memory/{key}` (`bots:read` / `bots:write`). Notes are added to agent context only if `memoryEnabled` is true. Each bot can store up to 16 notes of 2,000 characters each; optional expiration is limited to 365 days. Do not store secrets or credentials in memory notes.

Manage owned bots with `GET /v1/bots` and `GET /v1/bots/{botId}` (`bots:read`), `PATCH /v1/bots/{botId}` (`bots:write`, including the current `expectedVersion`), `POST /v1/bots/{botId}/disable` or `/enable`, and `DELETE /v1/bots/{botId}`. Edits create a new version; list/detail responses indicate whether a credential is configured without returning its opaque reference. Owners can grant a named account use of a private bot with `POST /v1/bots/{botId}/access/grants` while keeping it unlisted. Invitation links still require shared or invitation visibility. Recipients use `POST /v1/shared/bots/{botId}/messages`; revoking the grant blocks subsequent requests.

Bot owners can offer a same-workspace ownership transfer with `POST /v1/bots/{botId}/ownership-transfer` and an active recipient's `targetUserId`. Copy the one-time token to that recipient; it expires after 24 hours and is accepted with `POST /v1/bot-transfers/accept` from the recipient's signed-in workspace. The owner can inspect pending metadata with `GET /v1/bots/{botId}/ownership-transfer` and revoke an offer with `DELETE /v1/bots/{botId}/ownership-transfer/{transferId}`. Acceptance pauses schedules and requires the new owner to review them before resuming.

Replace an existing model API key with `POST /v1/bots/{botId}/credential-approval`, then `PUT /v1/bots/{botId}/credential` with `{ "expectedVersion": 3, "approvalId": "…", "credential": "…" }` (`bots:write`). The approval is bot-bound, expires after 10 minutes, and works once. The key is encrypted at rest; the response returns only whether a credential is configured and the replacement creates a new bot version. The Configuration tab provides the same flow with an explicit confirmation.

Change a bot's provider settings with the same one-use approval, followed by `PUT /v1/bots/{botId}/model` with `expectedVersion`, `approvalId`, a fresh `credential`, and a `model` object containing `providerId`, `model`, optional HTTPS `endpoint`, and optional `parameters`. Arbitrary credential references are rejected. Model calls still require the endpoint origin to be included in the runtime's configured allowlist.

Review the latest 1–100 saved configuration snapshots with `GET /v1/bots/{botId}/versions?limit=50` (`bots:read`). The dashboard History tab shows the saved name, model, date, and system prompt; API keys are never included, only a `hasCredential` indicator.

Browse public bot listings with `GET /v1/public/bots?query=&limit=50` and safe details with `GET /v1/public/bots/{slug}`. A public bot with the `web_chat` interface is available at `/chat/{slug}`; the page uses `GET /v1/public/bots/{slug}/web-chat` for safe display metadata and `POST /v1/public/bots/{slug}/web-chat/messages` for messages. Public Web Chat and API calls require a signed-in token with `agent:run` and enforce per-user usage limits. Use a public API bot through `POST /v1/public/bots/{slug}/messages` or a granted shared bot through `POST /v1/shared/bots/{botId}/messages`. Manage owner access with `GET /v1/bots/{botId}/access` (`bots:read`), `PUT` the same route with `{ "dailyUsageLimit": 100, "rateLimitPerMinute": 10 }` for a public listing (`bots:write`), `POST /v1/bots/{botId}/access/grants` to grant a `userId` or create a one-time invitation, and `DELETE /v1/bots/{botId}/access/grants/{grantId}` to revoke it. Invitation creation returns the raw token once; accept it with `POST /v1/access/invitations/accept` after signing in. The dashboard Access tab exposes the same controls and the shareable Web Chat link.

List catalog entries with `GET /v1/skills` (`bots:read`). Publish tenant-only prompt, HTTPS, or workflow entries with `POST /v1/skills` (`skills:publish`). Publishing validates metadata, schemas, execution configuration, workflow child references, and idempotency; skill IDs are immutable, so give each revision a new ID. Platform operators can curate global entries through `/_operator/skills` with the separate `SKILL_CATALOG_ADMIN_TOKEN`; tenant API tokens cannot publish global skills. List, install, enable/disable, or uninstall a bot skill under `/v1/bots/{botId}/skills` (`bots:read` or `bots:write`). Installation requires explicit grants matching the skill's declared permissions. Store any skill credential through the encrypted secret flow and pass only its `credentialRef`; plaintext credential fields are rejected. HTTP skill definitions declare no auth, bearer auth, or an API-key header; credential-like static headers are rejected. HTTP endpoints and request policy come from the catalog definition, and endpoint origins must be listed in `HTTP_SKILL_ALLOWED_ORIGINS`.

Manage MCP servers under `/v1/bots/{botId}/mcp-servers`: `GET`/`POST` the collection; `POST` `/{serverId}/connect`, `/test`, `/disconnect`, or `/oauth/start`; `GET` `/{serverId}/tools`; `PATCH` `/{serverId}/tools/{toolName}` with `{ "enabled": true, "grantedPermissions": ["mcp:invoke"] }`; and `DELETE` `/{serverId}`. Calls require bot ownership and `bots:read` or `bots:write`. Add only HTTPS endpoints whose exact origins are in `MCP_ALLOWED_ORIGINS`. Authentication can be omitted, supplied as `authentication: { "mode": "bearer", "token": "…" }`, configured for server-to-server OAuth with `authentication: { "mode": "oauth_client_credentials", "clientId": "…", "clientSecret": "…", "issuer": "https://auth.example.com", "scope": "tools:read" }`, or configured for user-consent OAuth authorization code with PKCE. OAuth issuer origins must also be allowlisted. The dashboard completes the owner-authenticated callback at the same-origin `/miniapp/` URL. Credentials are encrypted before persistence and never returned by the API. Discovery never enables tools automatically. Schema changes disable a previously approved tool and clear its grant.

Connect a published bot to Telegram with `PUT /v1/bots/{botId}/telegram` (`bots:write`) and a JSON body containing its BotFather token. Send the token over HTTPS; it is validated with Telegram and encrypted before storage. `GET` returns connection status plus allowed and pending Telegram user IDs; `PATCH` with `{ "allowedUserIds": [123456789] }` replaces the allowlist, and `DELETE` removes the webhook and encrypted credentials. New sender IDs appear as pending and cannot reach the agent until an owner approves them. Set `TELEGRAM_WEBHOOK_BASE_URL` to the public HTTPS base URL that routes to this runtime. Webhook updates are verified using Telegram's secret-token header and deduplicated in storage. Approved senders can send JPEG, PNG, or WebP photos up to 8 MB; UTF-8 TXT, Markdown, CSV, TSV, JSON, JSONL, XML, YAML, and log documents up to 64 KB; and PDF or DOCX documents up to 2 MiB. PDFs are limited to 20 pages and DOCX extraction reads only `word/document.xml` with a 1 MiB expanded-XML limit. Extracted text is capped at 60,000 characters; scanned PDFs need OCR and are not readable yet. Attachments are size-checked, malware-scanned before parsing, staged temporarily in tenant-scoped object storage, and deleted after processing. The system prompt marks their contents as untrusted reference data. Extracted document text enters conversation history; image bytes are excluded and must be resent for later turns. Image analysis is disabled by default: set `MODEL_IMAGE_INPUT=true` (or the Cloudflare `MODEL_IMAGE_INPUT` variable) only when the configured model supports image input. Telegram typing status is sent while the model responds. A sender also needs an owner-managed per-user tool grant before the agent can discover or execute an installed skill or enabled MCP tool.

Manage an approved Telegram user's tool grants with `GET` or `PUT /v1/bots/{botId}/telegram/users/{telegramUserId}/tool-grants` (`bots:read` or `bots:write`). `PUT` replaces the list, for example `{ "toolRefs": ["skill:weather.lookup", "mcp:mcp_<server-id>:lookup"] }`. Removing a sender from the allowlist also removes their tool grants. Both the bot-wide skill/MCP permission and the per-sender grant must be present at discovery and again at execution.

Create and manage durable schedules at `/v1/bots/{botId}/scheduled-tasks`. `POST` requires `bots:write` and `agent:run` and accepts `schedule` (`once:<ISO timestamp>` or `daily:HH:mm`), an IANA `timezone`, a `prompt`, and an approved `notifyTelegramUserId`. The bot must be published and connected to Telegram. `GET` lists owned tasks; `PATCH /{taskId}` with `{ "status": "paused" }` pauses one and `{ "status": "active" }` resumes it; `DELETE /{taskId}` pauses it. `POST /{taskId}/retry` requeues an exhausted failed run for its owner and resets its attempt counter. Confirm retries carefully: if Telegram accepted an earlier message before a timeout, it may be delivered twice. Bun polls its persistent SQLite job table. Cloudflare uses per-bot Durable Object alarms, a Queue consumer, and a one-minute reconciliation cron. Failed delivery retries with backoff, and the model result is persisted so delivery retries do not regenerate it.

See [DEVELOPMENT_STATUS.md](DEVELOPMENT_STATUS.md) for verified scope and [docs/architecture.md](docs/architecture.md) for the audit and design. Cloudflare bindings and the required provisioning steps are described in [apps/cloudflare-runtime/README.md](apps/cloudflare-runtime/README.md).

## Development

Bun 1.4.4 and Wrangler 4.156.0 are pinned for this worktree. Use:

```sh
bun install
bun run check
bun test
bun run build
bun run benchmark
```

The benchmark exercises the shared orchestration loop in-process at concurrency 1, 8, and 32. It reports latency and throughput without model-provider or database network time.

`bun run check` generates Wrangler binding types, then checks both TypeScript configurations and lints the workspace. `bun run build` bundles Bun and runs Wrangler's Cloudflare dry-run. It does not deploy. To bootstrap a self-hosted tenant and mint its first API token, run `bun run bootstrap:bun -- "My workspace" owner-subject factory:read,factory:write,bots:read,bots:write,agent:run,tokens:manage,members:manage`; the token appears once in the command output. To run the local Bun server, copy `.env.example`, generate a fresh 32-byte base64 encryption key, and run `bun run dev:bun`. Cloudflare local development uses `bun run dev:cloudflare`.

The dashboard and Telegram Mini App are served at `/miniapp/` by both runtimes. Bun builds the dashboard before starting. For local browser work, open `http://127.0.0.1:3000/miniapp/` and sign in with an owner API token. A Telegram launch can sign in through validated `initData` when `TELEGRAM_MASTER_BOT_TOKEN` is configured; the legacy misspelling `TELEGRAME_BOT_TOKEN` is still accepted by Bun. The development master bot supports `/create [idea]` onboarding; for another environment, set `TELEGRAM_MASTER_WEBHOOK_SECRET` and `TELEGRAM_WEBHOOK_BASE_URL`, then register with `bun run telegram:register-master`. Model keys and wider-visibility confirmations are completed in the authenticated Mini App. Configure the public HTTPS Mini App URL in BotFather after deploying to that hostname. `AI Hat*.html` design exports are intentionally ignored by Git and Docker.

The development Worker and Mini App are deployed at [https://aihat-bot-factory.work-fdc.workers.dev/miniapp/](https://aihat-bot-factory.work-fdc.workers.dev/miniapp/). Its D1 migrations, R2 bucket, Queue, and encryption secrets are configured. Add the Worker host as the Telegram bot's Mini App domain in BotFather. Staging and production are separate and are not deployments of the development Worker.

## Provision staging or production Cloudflare resources

From the repository root, inventory the account and print a dry-run plan:

```sh
bun run cloudflare:provision -- --env staging
```

After reviewing the named resources and confirming Wrangler is logged into the intended Cloudflare account, add `--apply` to create the environment's D1 database, R2 bucket, and Queue and apply its D1 migrations:

```sh
bun run cloudflare:provision -- --env staging --apply
```

Use `--env production` only when you are ready to create those production resources. The command updates the matching Wrangler D1/R2 bindings, leaves unrelated account resources alone, and never deploys the Worker or configures secrets. Review the updated `apps/cloudflare-runtime/wrangler.jsonc` and set nonsecret environment variables. Then deploy once with `bun run --cwd apps/cloudflare-runtime deploy:staging` or `deploy:production`; Wrangler requires the Worker to exist before `wrangler secret put` can configure its secrets. Add the required encryption keyring and integration secrets immediately after this first deployment and before enabling user sign-in or bot traffic. See the [Cloudflare runtime guide](apps/cloudflare-runtime/README.md#environments-and-local-checks).

For operational fixes and common configuration failures, see the [troubleshooting guide](docs/troubleshooting.md).

## Rotating local SQLite secret keys

Keep the existing and replacement 32-byte keys in `SECRET_KEYRING_JSON`, set `SECRET_ACTIVE_KEY_ID` to the replacement key ID, and stop the Bun service. Point `DATABASE_PATH` at the existing SQLite file. Preview the number of envelopes that need re-encryption with `bun run rotate-secrets:bun`; add `--apply` to perform the rotation. The command processes bounded pages and uses compare-and-swap updates, so it can be safely rerun after interruption. Run the preview again and confirm `needingRotation` is zero before removing the old key from the keyring. Back up the database and key material before applying. For Docker, stop the service and run the same tool against its persistent volume:

```sh
docker compose stop aihat-bot-factory
docker compose run --rm --no-deps --entrypoint bun aihat-bot-factory dist/apps/bun-runtime/src/rotate-secrets.js
```

After reviewing the preview and confirming the database backup and new key are available, apply and restart:

```sh
docker compose run --rm --no-deps --entrypoint bun aihat-bot-factory dist/apps/bun-runtime/src/rotate-secrets.js --apply
docker compose start aihat-bot-factory
```

This CLI operates on Bun SQLite databases. For Cloudflare D1, see the operator-authenticated rotation workflow in the [Cloudflare runtime guide](apps/cloudflare-runtime/README.md#bindings-and-ownership).

## Rotating Cloudflare D1 secret keys

Configure the Worker secret `SECRET_ROTATION_AUTH_TOKEN` with a distinct high-entropy token. In a trusted shell, set `CLOUDFLARE_WORKER_URL` to the HTTPS Worker origin and `CLOUDFLARE_SECRET_ROTATION_TOKEN` to the same token. Run `bun run rotate-secrets:cloudflare` to preview, then review `needingRotation` before using `bun run rotate-secrets:cloudflare --apply`. The command uses bounded D1 pages and compare-and-swap updates. Keep old key material in the Worker keyring until a fresh dry run reports zero envelopes needing rotation. This command calls the already-configured Worker and does not deploy it.

## Self-hosted Docker

Create a private `.env` from `.env.example`, replace the example keyring with a freshly generated 32-byte base64 key, and set the MCP and HTTP origin allowlists only for services you trust. Then run:

```sh
docker compose up --build -d
docker compose logs -f aihat-bot-factory
```

The image builds the Bun runtime in a multi-stage build and runs it as an unprivileged user. Compose keeps SQLite data in the `aihat_data` volume, exposes port 3000 by default, and applies a read-only root filesystem with a writable data volume. The container does not require Cloudflare services. API access still requires bootstrapping an owner token with `docker compose exec aihat-bot-factory bun dist/apps/bun-runtime/src/bootstrap.js "My workspace" owner-subject factory:read,factory:write,bots:read,bots:write,agent:run,tokens:manage,members:manage`.

To enable local malware scanning, set `CLAMAV_HOST=clamav` in `.env` and start the optional scanner profile:

```sh
docker compose --profile clamav up --build -d
docker compose ps clamav
```

Wait until the ClamAV service is healthy before uploading files. The daemon port is available only on the private Compose network; do not publish it to the host or Internet. This adapter is for Bun. Cloudflare continues to use the HTTPS scanner gateway contract below.

The Bun runtime can also expose ClamAV as that gateway for a Cloudflare Worker. Set `FILE_SCANNER_GATEWAY_TOKEN` to a high-entropy value in the Bun `.env`, keep the Bun service behind a TLS reverse proxy, and expose only `/internal/file-scan` to the Worker. Restrict that proxy route to the Worker/network where possible. In the Worker environment, set `FILE_SCANNER_ENDPOINT` to the full HTTPS route, set `FILE_SCANNER_ALLOWED_ORIGINS` to its exact HTTPS origin, and store the same token with `wrangler secret put FILE_SCANNER_TOKEN --env development`. The gateway bounds file bodies at 25 MiB, accepts four concurrent scans, and returns a transient `503` while at capacity. The token is never returned by the gateway. Do not publish ClamAV's unauthenticated TCP port.
