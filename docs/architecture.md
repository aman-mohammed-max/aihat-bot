# Repository audit and architecture

## Audit scope and evidence

The working tree was inspected before implementation. At audit time it contained only `README.md`; Git history contained only the initial commit. No source files, manifests, dependency lockfiles, tests, database schema or migrations, Docker files, or Wrangler configuration existed. `README.md` contained only the repository title.

Environment checks found Node.js v24.22.2 and Docker 29.9.2. `bun` and `wrangler` were not installed. There is consequently no existing build or test command to inspect or run, and no application behavior that can be claimed as working.

## Existing architecture and inventory

There is no application architecture yet. The repository has no dependencies, TypeScript compiler configuration, runtime entrypoints, persistence layer, authentication, integrations, or dashboard. No third-party dependencies or dependency vulnerabilities can be assessed because there is no dependency manifest or lockfile.

## Problems and risks

1. The requested product is wholly unimplemented; every expected deliverable remains outstanding.
2. There is no runtime or shared core, so Bun/Workers parity and runtime compatibility cannot be evaluated.
3. There is no identity, tenant authorization, secret storage, encryption, SSRF policy, rate limiting, audit log, or webhook verification. The product must not accept real credentials or expose a public endpoint until those controls exist.
4. There is no data model or migration strategy for tenant-owned bots, versions, credentials, conversations, jobs, skills, MCP, or usage.
5. There is no test, lint, format, typecheck, build, or deployment validation setup.
6. Bun and Wrangler are unavailable in the audit environment. Cloudflare deployment credentials and resource identifiers are also not established in the repository.

## Proposed architecture

Keep business rules in a dependency-light TypeScript core. Define explicit ports for persistence, secret operations, queues, scheduling, object storage, HTTP, and logging. Bun and Cloudflare entrypoints should compose runtime-specific adapters around the same application services; they must report unsupported capabilities explicitly. Provider, skill, MCP, Telegram, and dashboard features should be added behind small interfaces when their authorization and tenant boundaries are defined.

Use D1 for Cloudflare relational records and SQLite-backed Durable Objects only for state that needs single-key coordination. Use a self-hosted relational adapter for Bun. Keep dialect-specific migrations explicit rather than pretending SQL dialects are interchangeable. Treat credentials as secret references and never include them in API response types or logs. Gate high-impact actions such as publishing and personal-data integrations on explicit owner approval.

## Prioritized implementation plan

1. Foundation: workspace, shared domain contracts, runtime capability reporting, environment validation, error handling, and logging.
2. Core agent path: bot lifecycle, provider interface and capability negotiation, prompt assembly, tool registry and authorization, conversation persistence.
3. Security and persistence: tenant/auth model, secret abstraction, migrations, audit records, network policy and rate limits.
4. Bot factory and skills: resumable drafts, approval-gated publication, validated HTTP/native/workflow skills, and MCP trust/permission boundaries.
5. Runtime adapters: Bun hosting and Cloudflare Worker, D1, Durable Objects, R2, Queue, and alarm adapters with explicit unsupported capabilities.
6. Telegram and dashboard: independently routed bot integrations and tenant-scoped management UI.
7. Automation and production readiness: persistent schedules, recovery, parity/security tests, Docker/Wrangler validation, deployment and troubleshooting docs.

This plan is intentionally a sequence, not a claim that any item is complete. Do not launch public bots until authentication, tenant isolation, credential handling, permission enforcement, and abuse controls are implemented and verified.

## Dashboard implementation update

The owner dashboard is a small TypeScript browser app bundled by Bun and served at `/miniapp/` from both runtimes. It consumes the existing owner-scoped APIs for bot creation and management, Telegram, skills, MCP, schedules, API tokens, conversation history, usage analytics, and bot memory. The Skills page supports tenant-only catalog publishing for tokens with `skills:publish`; prompt, HTTPS, and workflow definitions are validated and immutable by ID. Platform operators curate shared entries through a separate bearer-protected global catalog API; tenant tokens cannot modify global definitions. The BotFather-style home includes the Mini App URL and BotFather setup steps. Its navy, Telegram-blue, and lime palette remixes the local HTML design exports. Those `AI Hat*.html` exports are ignored by Git and Docker.

Bot configuration snapshots are stored per version in the existing `bot_versions` table. Owners can inspect the latest 100 snapshots; the history projection removes credential references and marks only whether a credential was configured. Existing current-version snapshots receive name/description labels in migration `0015_bot_version_labels.sql`.

Telegram Mini App identity now uses BotFather master-bot HMAC validation, a five-minute `auth_date` window, a unique one-use hash for replay protection, and a 12-hour API token. Verified first-time users receive a deterministic personal tenant and owner membership in either runtime; ordinary browsers can continue to use an owner API token. Membership administration is available through a separate `members:manage` scope and tenant-scoped repository port. Owners can add existing account IDs, invite signed-in accounts with expiring one-use links, change roles, and deactivate members; only invitation hashes are stored, and deactivation revokes active tenant API tokens while preserving owned data. `GET /v1/workspaces` lists active memberships, and `POST /v1/workspaces/switch` issues a target-workspace token with scopes intersected against both the source token and the target role, bounded by the source expiry and a 12-hour maximum. Workspace membership does not grant access to another member's private bots; private bot use still requires an explicit bot access grant. The development Mini App is deployed at `https://aihat-bot-factory.work-fdc.workers.dev/miniapp/`; it can be entered in BotFather after configuring the bot's Mini App domain. The master-bot text command flow is implemented and registered in development, and public/shared bot execution routes are implemented. The development D1/R2/Queue resources are provisioned; staging and production are not deployed.

Telegram photo and document uploads are size-checked and staged temporarily in tenant-scoped object storage. JPEG, PNG, and WebP bytes are forwarded as OpenAI-compatible image parts only when the operator enables `MODEL_IMAGE_INPUT`; image bytes are omitted from stored conversation history. Text files are decoded as bounded UTF-8. Shared PDF extraction uses `unpdf`/PDF.js with a 2 MiB input cap, a 20-page cap, a 5-second deadline, no image rendering, and a 60,000-character output cap. DOCX extraction validates the ZIP directory and CRC, inflates only `word/document.xml` in bounded chunks, limits expanded XML to 1 MiB, and caps extracted text at 60,000 characters. Malware scanning must return clean before a PDF or DOCX is parsed, and the shared agent system prompt treats attachment contents as untrusted reference data. Scanned PDFs need OCR and are not readable yet. Telegram sends typing actions while the agent runs and retries only short, explicit `429` responses. Owners can manually requeue exhausted scheduled jobs; a retry can duplicate a message when Telegram accepted an earlier send before the connection failed. Persistent uploaded-file management is implemented with quarantine and an optional scanner gateway; the development scanner is unconfigured. Audio/video parsing and exactly-once external delivery remain unsupported.

## Initial agent engine decisions

The shared core now has an OpenAI-compatible chat-completions adapter and a provider-neutral orchestration loop. Provider feature flags default to false; tool calling must be explicitly enabled for a configured provider profile. Streaming uses the shared provider contract and SSE parser, and is advertised only when the model endpoint origin is both network-allowlisted and explicitly listed in `MODEL_STREAMING_ORIGINS`. The owner agent API and Mini App preview stream text deltas, propagate request cancellation to model and HTTP/native skill requests, and emit sanitized terminal errors. Strict, non-streaming JSON-schema output supports a bounded subset and is enabled only when the model endpoint origin is also listed in `MODEL_STRUCTURED_OUTPUT_ORIGINS`; the provider response is parsed and validated before it reaches the caller. The adapter accepts only HTTPS URLs whose exact origins are approved by deployment configuration, rejects redirects, applies a timeout, and resolves credentials through a tenant-scoped secret reference. Non-streaming model requests retry configured transient HTTP responses up to `MODEL_RETRY_MAX_ATTEMPTS`, with bounded exponential backoff and a maximum three-second `Retry-After`; network failures and streaming requests are not retried because their completion state is uncertain. Retries may still incur another provider charge. A tenant-supplied URL is never sufficient authorization to make a request.

Tool definitions are application-registered. The model receives only tools for which the actor currently has all required permissions, and permissions are checked again immediately before execution. Tool input is passed through an application-owned parser, calls are bounded by a round limit and timeout, and error details are not sent back to the model. Conversation turns are appended only after a successful agent response; persistence adapters must make each append atomic. Agent-issued tool calls receive stable execution keys. Workflow skills use tenant-scoped SQLite/D1 leases and compare-and-swap checkpoints; serialized inputs and outputs are encrypted through the secret store. Workflow steps can call installed, idempotent HTTP or registered native skills and use forward-only condition branches. The bounded DSL does not evaluate code, and child permissions are rechecked at every step. Other tool results and generated-image attachment URLs are stored only in encrypted secret records behind tenant/bot-scoped SQLite/D1 leases, checked against an input fingerprint, and replayed for seven days; expired records are purged opportunistically on later tenant tool calls. Expired leases and failed executions enter owner review: an owner can permit one replay of the original request or close it. Approval does not dispatch a request, and an external effect may already have happened, so duplicate remote actions remain possible.

The bot factory now defines a 19-step persisted state machine, including live chat, image, and search model selection. Model discovery fetches the provider's OpenAI-compatible `/models` response only after checking the exact HTTPS origin against `MODEL_ALLOWED_ORIGINS`; temporary discovery credentials are not stored in session answers. Session reads are tenant and owner scoped; updates use optimistic revisions so concurrent submissions cannot silently overwrite each other. Paused sessions resume at their current step. The session accepts only an opaque secret reference, never a raw credential. A one-use approval verifier is required before connecting credentials, enabling non-private visibility, or publishing. Draft and publish calls carry idempotency keys. Owner-scoped bot management supports listing, versioned edits, enable/disable, and cascade deletion. API mutation attempts, authenticated missing-scope and resource denials, factory approval issuance/consumption/rejection, public/shared bot access outcomes, membership changes, and skill/MCP permission checks are owner-visible in the audit log; credential-redacted bot version history is available through the API and dashboard. Authenticated API handlers record resource `403`/`404` outcomes without request bodies, query strings, or error detail; Bun/D1 parity and redaction tests cover those records.

The relational migrations target SQLite syntax shared by Bun SQLite and Cloudflare D1. They include tenant-aware foreign keys for bot-owned records and conversation messages, encrypted secret envelopes, factory sessions, skills/MCP, Telegram deployments and update reservations, usage, jobs, audit data, API token hashes, bot access grants, public listings, fixed-window skill rate-limit buckets, and per-bot workspace collaborators. Collaborator roles are explicit (`viewer` or `editor`), require an active same-tenant membership, and do not inherit from workspace admin/member roles. Editors can version only the bot's name, description, and system prompt; repository writes recheck collaborator and membership state atomically. A partial unique index prevents one Telegram bot identity from replacing a different active deployment's webhook. The WebCrypto secret store encrypts each credential with AES-GCM; tenant ID and secret reference are authenticated as additional data, and the encryption key comes only from an injected keyring. D1 repositories implement the same bot, draft/publish, factory-session, approval, API-conversation, Telegram, conversation, encrypted-secret, skill, and rate-limit contracts as Bun. Both runtimes use the shared environment keyring parser; Cloudflare key material is supplied through Worker secrets. Queries still include tenant scope even when foreign keys enforce ownership.

The Bun adapter implements the core SQLite repositories and runs checksum-verified migrations at startup. It stores schema migration checksums, enables foreign keys/WAL/busy timeout, and uses 0700 parent directories and 0600 database files. Its environment keyring reads versioned AES keys from deployment-managed variables. A tenant-scoped file object store uses atomic writes, private file permissions, and a SHA-256 integrity check.

The Cloudflare runtime uses Wrangler 4.156.0 and has development, staging, and production binding configurations for D1, SQLite-backed Durable Objects, R2, Queue producers/consumers, and a one-minute recovery cron. `CloudflareAlarmScheduler` routes one-shot bot schedules to a stable per-bot Durable Object; its alarms enqueue opaque job references. A separate `CONVERSATION_COORDINATOR` object uses a tenant/bot/conversation identity to serialize concurrent agent turns; it stores only a random lease token and expiry, while D1 remains the queryable source of conversation history. Expired leases are recovered by an alarm. The Queue consumer claims durable D1 jobs, runs the shared agent engine, persists results for delivery recovery, sends Telegram notifications, and schedules bounded retries. The cron re-enqueues due or expired jobs after worker restarts or exhausted Queue deliveries. Owners can requeue a failed scheduled job through the shared authenticated API; its result checkpoint is reused when present. MCP reconnect attempts are claimed through D1 leases and run lazily on later agent requests with capped exponential backoff, so no per-server Durable Object or in-memory retry timer is required. Telegram master-bot and customer-bot requests use persistent per-user fixed-window rate limits in D1, and API/login traffic uses a shared per-network fixed-window limit keyed by an HMAC of the runtime-supplied address. R2 and Bun file storage implement the same core `ObjectStore` port. Development D1 migrations through `0031_network_request_limits.sql` are applied; Worker version `ba10acae-f264-49f3-99c0-e85aef5759cc` passed live health, readiness, capability, and Mini App checks. Telegram `/create <idea>` uses the configured factory LLM to prefill creative setup fields. Staging and production still have placeholder D1 identifiers and no deployment.

## Retry policy and observability

Master-bot and customer-bot Telegram requests use persistent per-user fixed-window rate limits. Customer-bot rows are deployment scoped and store a SHA-256 sender hash; enforcement occurs after webhook update reservation and sender allowlist approval, before attachment or model processing.

The shared environment parser bounds deployment-level model, Telegram, and scheduled-job retry policies. HTTP skills carry catalog-level idempotency and retry settings, and workflow steps have separate bounded attempts/backoff. Telegram retries only an explicit Bot API `429` response with a short, valid `retry_after`; ambiguous network failures are never replayed. Model, HTTP-skill, workflow-step, Telegram, and scheduled-job retry attempts emit sanitized structured `dependency.retry` events (terminal scheduled-job failures use `scheduled_task.failed`). Events contain service, attempt, delay, and applicable HTTP status/method metadata; request content, prompts, credentials, and remote response text are not logged. Per-bot model retry policies and owner-facing retry analytics are available in both runtimes.

Both HTTP entrypoints expose health, readiness, and capability routes, shared API-token identity and management endpoints, the bot-creation state machine, owner-scoped bot, ownership-transfer, skill, MCP, schedule, conversation-history, usage, and memory management, an owner-scoped agent endpoint, and Telegram webhooks when a public HTTPS base URL is configured. Successful agent calls record aggregate request and provider-reported token totals; model retries record bot, attempt, delay, and HTTP status for owner-scoped analytics without prompts, credentials, or actor IDs. Telegram pseudonymous sender IDs are not written into the user foreign-key field. Owner-authored memory notes are injected only for bots with memory enabled, are bounded to 16 entries, and are marked as untrusted context. Scheduled tasks support one-time and daily timezone-aware schedules; job state and model output are persisted, retries resume from saved output, and delivery targets must be owner-approved Telegram users. Telegram tokens and webhook secrets are encrypted; webhook headers are checked before bot credentials are resolved, and update IDs are persisted for duplicate suppression. Telegram master-bot private chats and approved customer-bot senders have persistent per-user fixed-window limits; API/login traffic also has a persistent network-level limit. Telegram users receive pseudonymous actor IDs and conversations are grouped by chat, topic, and sender. First-seen Telegram users are pending until the owner adds their numeric IDs to a default-closed allowlist. Skill and MCP calls require both the existing bot-level grant and a per-user Telegram grant, checked at discovery and execution. Forward-only workflow skills and reviewed code-registered native TypeScript handlers are available to installed catalog skills. Telegram browser login is implemented but remains disabled in development until the numeric Login Client ID and BotFather origin are configured. Audio/video parsing, OCR for scanned PDFs, and sandboxed custom code remain unavailable. Staging/production resources and development file scanning are not configured, so this runtime foundation is not production-ready.

## Bot ownership transfer

An owner can offer a bot to another active member of the same workspace through `POST /v1/bots/{botId}/ownership-transfer`. The endpoint returns a 256-bit, 24-hour token once; only its SHA-256 hash is stored, and acceptance is bound to the target user and tenant. The owner can inspect safe pending metadata or revoke the offer. The recipient accepts from `POST /v1/bot-transfers/accept` after signing in to the same workspace. Acceptance waits for active scheduled runs, updates bot and linked factory-session ownership, removes unconsumed draft approvals and the previous owner's explicit grants, pauses active schedules, cancels queued/retrying schedule jobs, and writes audit events without the token. SQLite and D1 parity tests cover acceptance, expiry, revocation, replay denial, and scheduled work handoff.
