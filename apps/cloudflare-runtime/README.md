# Cloudflare runtime

This Worker exposes the responsive owner dashboard and Telegram Mini App at `/miniapp/`, plus shareable public Web Chat pages at `/chat/{slug}` for published bots that enable the `web_chat` interface. Visitors sign in with Telegram or an API token; Web Chat messages use the shared per-user public-bot limits. The Worker also exposes `GET /health`, `GET /ready`, `GET /capabilities`, shared API-token routes, the authenticated bot-creation state machine, bot lifecycle routes, skill and MCP management routes, owner-scoped agent, conversation-history, and memory endpoints, owner-scoped usage analytics, Telegram webhooks with bounded photo and text-file input, owner-scoped scheduled tasks, and owner-managed recovery for uncertain remote tool calls. Telegram Mini App launch data is HMAC-verified, age-limited, replay-protected, and exchanged for a 12-hour owner API token when the master bot secret is configured. Prompt, allowlisted HTTPS, code-registered native TypeScript, forward-only workflow, and allowlisted MCP Streamable HTTP tools can execute. Workflow children must be installed HTTP or registered idempotent native skills. MCP credentials support static bearer tokens, OAuth client credentials, and OAuth authorization-code consent with PKCE. OAuth callbacks return to the same-origin `/miniapp/`; interactive MCP authorization requires owner authentication and `bots:write`. Streaming and strict structured output require separately verified, egress-allowlisted origins; arbitrary user-supplied code remains unavailable.

`GET /v1/audit-logs?limit=50` returns the authenticated owner's recent API write attempts and factory approval outcomes. Events contain the method and path or approval action; request bodies, query strings, approval IDs, and approval hashes are not stored. Agent message requests are excluded.

Workspace owners can administer existing users with `GET`/`POST /v1/members`, `PATCH /v1/members/{userId}`, and `DELETE /v1/members/{userId}` using `members:manage`. Only owners can add, change roles, or deactivate; admins can list members. Owners can create, list, and revoke expiring workspace invites through `POST`/`GET /v1/invitations` and `DELETE /v1/invitations/{invitationId}`. Signed-in accounts accept a one-use token with `POST /v1/invitations/accept`; only the token hash is persisted. Removing a member revokes that user's active API tokens and records the change in D1 audit logs. Accounts with multiple active memberships can use `GET /v1/workspaces` and `POST /v1/workspaces/switch` to issue a token for an assigned workspace. Effective scopes are intersected with the source token's scope ceiling and the target role; exchanged tokens expire within 12 hours and never later than the source token. Workspace membership does not grant access to another member's private bots; those remain explicit per-bot grants.

## Bindings and ownership

- **D1 (`DB`)** stores globally queryable relational records. `CloudflareD1Repositories` implements bot, draft/publish, factory-session, approval, API-token, conversation history, usage reporting, Telegram deployment/update, encrypted-secret, skill catalog/install/rate-limit, MCP server/tool, and scheduled-task/job contracts. Every lookup and write carries tenant and bot scope. Whole conversation turns and MCP rediscovery writes use D1 batches. Migration `0027_native_text_statistics.sql` seeds the reviewed `aihat.text.statistics.v1` native skill in the shared catalog.
- **Durable Objects** use SQLite-backed coordination with separate identities: `BOT_COORDINATOR` is stable per tenant and bot for scheduled alarms, while `CONVERSATION_COORDINATOR` is stable per tenant, bot, and conversation and serializes agent turns. Conversation objects store only an opaque lease and expiry; D1 remains the source of truth for queryable conversation messages. Neither object stores prompt text or credentials.
- **Queues (`JOBS`)** receives opaque scheduled-job references from Durable Object alarms. Its consumer claims durable D1 jobs, runs the shared agent engine, persists the response for delivery recovery, sends it to an owner-approved Telegram user, and applies bounded retry backoff. A per-environment one-minute cron reconciles due or expired jobs back into the Queue after dropped messages or worker restarts. The capability response reports `queueProcessing: true`.
- **R2 (`OBJECTS`)** stores binary objects under tenant-prefixed keys with content type and ownership metadata. Both object-store adapters enforce a 25 MiB limit, validate object references, and support streaming and buffered reads/writes. R2 streams are forwarded directly through size-checking transforms.

Cloudflare reads versioned 32-byte AES keys from Worker secrets `SECRET_ACTIVE_KEY_ID` and `SECRET_KEYRING_JSON`; `encryptedSecrets` is available when these are configured. Use the same key IDs and key material as any runtime that needs to decrypt the same D1 envelopes. `MODEL_ALLOWED_ORIGINS` is an operator-managed HTTPS origin list; it defaults to `https://api.openai.com`. `MODEL_STREAMING_ORIGINS` and `MODEL_STRUCTURED_OUTPUT_ORIGINS` are separate exact-origin verification lists; structured output stays disabled until an origin is explicitly added to both its verification list and `MODEL_ALLOWED_ORIGINS`. Its strict schema subset is limited to 12 KB/500 nodes, and returned JSON is limited to 64 KB. Set `MODEL_IMAGE_INPUT=true` as a Worker variable only when the configured model supports image input. `HTTP_SKILL_ALLOWED_ORIGINS` and `MCP_ALLOWED_ORIGINS` are separate comma-separated HTTPS origin allowlists and default to empty. Add both the MCP endpoint origin and OAuth issuer origin to `MCP_ALLOWED_ORIGINS`; the SDK's discovered metadata and token URLs are checked against this list before network requests. For OAuth authorization-code consent, register the exact `https://<your-app-host>/miniapp/` callback URL with the authorization server; the dashboard derives it from the same-origin browser request. Set `TELEGRAM_WEBHOOK_BASE_URL` to the public HTTPS Worker URL for each environment before connecting a customer Telegram bot; the capability route reports customer-bot webhooks only when this value is non-empty. Telegram Mini App identity sign-in and the master-bot onboarding flow use `TELEGRAM_MASTER_BOT_TOKEN`; the webhook also requires `TELEGRAM_MASTER_WEBHOOK_SECRET`. `TELEGRAM_MASTER_REQUESTS_PER_MINUTE` limits each Telegram user to 30 master-bot messages per minute by default and can be set from 1 to 1,000. Reviewed native handlers are registered in application code; arbitrary user-supplied code and sandbox execution remain unavailable.

API tokens use 256 bits of random entropy and are stored as SHA-256 hashes. Authentication joins the token to a current tenant membership and checks revocation and expiration on every request. `POST /v1/tokens` and `DELETE /v1/tokens/{tokenId}` require the `tokens:manage` scope; newly minted token plaintext is returned once with `Cache-Control: no-store`. A token can grant only scopes it already holds. The first Cloudflare owner can be provisioned by an operator in D1 or created through verified Telegram Mini App sign-in when the master bot secret is configured. The Bun-only local bootstrap command is documented in the root README.

Factory requests use `POST /v1/factory-sessions`, `GET /v1/factory-sessions/{sessionId}`, and `POST` actions at `/{sessionId}/pause`, `/resume`, `/answer`, `/credentials`, `/models`, `/draft`, `/publish`, and `/approvals`. API tokens need `factory:read` for session reads and `factory:write` for state changes. `/models` fetches the configured endpoint's model list for the active chat, image, or search step; origins must be present in `MODEL_ALLOWED_ORIGINS`, and redirects are blocked. Temporary chat discovery keys are not stored in session answers. Selected image/search models are used through the model-call tools `generate_image` and `search_web`, which call `/images/generations` and `/search` on the same exact egress-approved endpoint. Image providers must return an HTTPS image URL; image URLs are sent as Telegram photos and returned as API attachments, while inline-base64-only responses remain unsupported. For Telegram retry recovery, the URL is encrypted as a short-lived secret reference and removed after delivery; D1 stores only the reference. Approval IDs are short-lived and one-use; D1 stores only their hashes. The `/credentials` action encrypts a submitted model key and returns a reference, never the key.

Reviewed native TypeScript handlers are registered in `packages/core` and wired into both runtimes. Migration `0027_native_text_statistics.sql` installs `aihat.text.statistics.v1` into the shared catalog; an owner still needs to install it and grant `text:analyze`. Global operators can publish additional catalog metadata only when it exactly matches a compiled registry entry. Tenant-published arbitrary code is rejected, and sandbox execution remains unsupported.

Configure the keyring as Worker secrets before connecting credentials:

```sh
wrangler secret put SECRET_ACTIVE_KEY_ID
wrangler secret put SECRET_KEYRING_JSON
wrangler secret put SECRET_ROTATION_AUTH_TOKEN
wrangler secret put SKILL_CATALOG_ADMIN_TOKEN
wrangler secret put TELEGRAM_MASTER_BOT_TOKEN
wrangler secret put TELEGRAM_MASTER_WEBHOOK_SECRET
```

The development Worker has both master-bot secrets configured and its webhook registered. For staging or production, set `TELEGRAM_MASTER_BOT_TOKEN`, `TELEGRAM_MASTER_WEBHOOK_SECRET`, and the public HTTPS `TELEGRAM_WEBHOOK_BASE_URL` separately, then register that environment's webhook with `bun run telegram:register-master`. Bun accepts the legacy `TELEGRAME_BOT_TOKEN` spelling; Cloudflare should use the correctly spelled secret. Never put a production token in Wrangler vars or commit it. The webhook handles `/start`, `/help`, `/create [idea]`, `/continue`, `/mybots`, and `/cancel`; when all `FACTORY_LLM_*` settings are configured, `/create <idea>` drafts the creative profile and saves it into the owner-scoped setup for review. Provider, model, credential, skill, MCP, visibility, and publishing choices remain with the owner. The bot stores the active factory session per Telegram user, limits private-chat messages per user, and resumes the 19-step setup after each answer. Model credentials and non-private visibility choices open the authenticated Mini App, where sensitive inputs and explicit confirmations are handled. Verified Mini App and browser sign-ins provision the same personal tenant and owner membership. Outside Telegram, browser sign-in uses Telegram's signed OIDC ID token; set the numeric `TELEGRAM_LOGIN_CLIENT_ID` Wrangler variable and register the app's HTTPS origin in BotFather to enable it. The login remains disabled when that variable is empty. Local Bun reads the same variable from `.env`.

The factory AI draft endpoint reads `FACTORY_LLM_ENDPOINT`, `FACTORY_LLM_MODEL`, and `FACTORY_LLM_TOKEN`. Set the endpoint and model in the selected Wrangler environment's `vars` in `wrangler.jsonc`; store the token as a Worker secret with `wrangler secret put FACTORY_LLM_TOKEN` (add `--env staging` or `--env production` when configuring those environments). The draft action is disabled until all three values are present. For local Bun, set the same names in the ignored `.env` file. The assistant drafts only name, description, purpose, audience, and personality; the bot owner still chooses provider settings, credentials, visibility, permissions, and publication.

Set these separately for development, staging, and production (`wrangler secret put NAME --env staging` or `--env production`).

For Bun, set the same variables in the runtime environment. Generate a fresh key with `openssl rand -base64 32`; keep previous key IDs in `SECRET_KEYRING_JSON` during rotation until their ciphertext has been re-encrypted.

Cloudflare D1 secret rotation is exposed only at `POST /_operator/secrets/rotation`, protected by the Worker secret `SECRET_ROTATION_AUTH_TOKEN`. Generate a distinct high-entropy value with `openssl rand -hex 32`, store it with `wrangler secret put SECRET_ROTATION_AUTH_TOKEN`, and keep it out of source control. From a trusted shell, set `CLOUDFLARE_WORKER_URL` to the Worker HTTPS origin and `CLOUDFLARE_SECRET_ROTATION_TOKEN` to that same value, then run `bun run rotate-secrets:cloudflare` to preview. Review the counts before running `bun run rotate-secrets:cloudflare --apply`. The command processes bounded pages, reports only counts and key IDs, and never prints secret values. Retain old key material until a dry run reports zero records needing rotation.

The global skill catalog is curated through `/_operator/skills`, protected by the separate `SKILL_CATALOG_ADMIN_TOKEN`. Generate a distinct value with `openssl rand -hex 32` and configure it separately in each environment with `wrangler secret put SKILL_CATALOG_ADMIN_TOKEN`. `GET` lists global entries, `POST` publishes a validated prompt, HTTPS, or workflow definition, and `PATCH /_operator/skills/{skillId}` enables or disables an entry. Global workflow skills can only reference enabled global catalog children. Workspace owners use `POST /v1/skills` with `skills:publish` for tenant-only entries; those credentials cannot modify the global catalog.

Send text requests to `POST /v1/bots/{botId}/messages` with `agent:run`. Each token can call only bots owned by its user. Add provider origins to `MODEL_ALLOWED_ORIGINS` only after reviewing the endpoint; unlisted origins are blocked before resolving the secret or making a request. Non-streaming requests can include `responseSchema` to receive a validated strict JSON object in `structuredOutput`; this requires the endpoint origin in `MODEL_STRUCTURED_OUTPUT_ORIGINS` as well. Unsupported schemas, unverified origins, and structured streaming requests are rejected explicitly.

Use `GET /v1/skills` to inspect the tenant-visible catalog, then manage installations with `GET` or `POST /v1/bots/{botId}/skills`, `PATCH /v1/bots/{botId}/skills/{skillId}`, and `DELETE /v1/bots/{botId}/skills/{skillId}`. These routes require `bots:read` or `bots:write` and enforce bot ownership. Installation requires explicit grants for every declared permission. Tenant-owned skills are published with `POST /v1/skills` and `skills:publish`; platform operators curate cross-tenant definitions through the protected `/_operator/skills` route. HTTP skill endpoint origins must appear in `HTTP_SKILL_ALLOWED_ORIGINS` before the model can discover them. HTTP credentials use encrypted references and declared bearer or API-key-header modes; credential-like static headers are rejected.

Use `GET /v1/bots/{botId}/conversations` and `GET /v1/bots/{botId}/conversations/{conversationId}/messages` to inspect owner-scoped history. Permanently delete an owned conversation and its stored messages with `DELETE /v1/bots/{botId}/conversations/{conversationId}` (`bots:write`). `GET /v1/usage?days=30` returns owner-only request totals, provider-reported tokens, and model retry totals by bot, UTC date, and HTTP status for 1–90 days. Retry analytics record only bot, attempt limits, delay, status, and timestamp; prompts, request bodies, credentials, and actor identifiers are omitted. `GET`, `PUT /v1/bots/{botId}/memory/{key}`, and `DELETE /v1/bots/{botId}/memory/{key}` manage up to 16 owner-authored notes per bot; notes enter model context only when memory is enabled. These routes use `bots:read` and `bots:write`; analytics omit actor identifiers and conversation content.

Manage MCP servers under `/v1/bots/{botId}/mcp-servers` with collection `GET`/`POST`, server `POST` actions `connect`, `test`, `disconnect`, `oauth/start`, and `oauth/callback`, tool `GET`, tool-permission `PATCH`, and server `DELETE` routes. These routes enforce bot ownership and `bots:read` or `bots:write`; OAuth start and callback are same-origin browser actions. Add only HTTPS endpoints whose exact origins are configured in `MCP_ALLOWED_ORIGINS`; the allowlist is checked before resolving a secret reference. Credentials can be encrypted bearer tokens, OAuth client-credentials settings, or OAuth authorization-code settings. The authorization-code client uses PKCE and persists its one-use state, verifier, discovery data, client information, and tokens inside encrypted tenant secrets. OAuth callback URLs are derived as the same-origin `/miniapp/` path; register that exact URL with the provider. The MCP endpoint, issuer, metadata, and token endpoint origins must be allowlisted, and redirects fail closed. Discovery stores schemas and disables new tools; enabling a tool requires `mcp:invoke`. If a rediscovered input or output schema changes, the old grant is cleared. Unhealthy servers are retried lazily on later agent requests using a persisted lease, exponential backoff capped at 15 minutes, and a maximum of five attempts; owners can also use `connect` to retry manually. Set `MCP_ALLOWED_ORIGINS` in Wrangler vars for each environment after reviewing each server and issuer origin.

Manage owned bots through `GET /v1/bots`, `GET /v1/bots/{botId}`, `PATCH /v1/bots/{botId}`, `POST /v1/bots/{botId}/enable`, `POST /v1/bots/{botId}/disable`, and `DELETE /v1/bots/{botId}`. Edits require the current `expectedVersion` and persist a new version. Responses redact credential references. All management routes enforce token scopes and bot ownership.

Grant a named account use of a private bot with `POST /v1/bots/{botId}/access/grants`; the bot stays unlisted and the recipient must sign in to use `POST /v1/shared/bots/{botId}/messages`. `GET /v1/bots/{botId}/access` lists grants and `DELETE /v1/bots/{botId}/access/grants/{grantId}` revokes one. Invitation links remain available only for shared or invitation visibility.

Transfer a bot within the same workspace with `POST /v1/bots/{botId}/ownership-transfer` and a `targetUserId` for an active member. The owner receives a one-time token to share directly with that recipient; only the signed-in recipient can accept it through `POST /v1/bot-transfers/accept`. `GET /v1/bots/{botId}/ownership-transfer` returns pending transfer metadata without the token, and `DELETE /v1/bots/{botId}/ownership-transfer/{transferId}` revokes an offer. Offers expire after 24 hours. Acceptance moves the bot and linked factory sessions, pauses its schedules, cancels queued schedule jobs, and revokes the previous owner's explicit bot grants. It waits for any running scheduled job to finish.

Connect a published bot to Telegram using `PUT /v1/bots/{botId}/telegram` with `bots:write` and a JSON body containing the BotFather token. The token is sent over HTTPS, checked with Telegram, and encrypted at rest. `GET` returns connection status and allowed/pending sender IDs; `PATCH` with `{ "allowedUserIds": [123456789] }` replaces the sender allowlist. First-seen users remain pending and cannot reach the agent before owner approval. `DELETE` unregisters the webhook and removes the deployment credentials. Telegram webhooks use a random secret header and persisted update IDs to reject forged or duplicate deliveries. Approved senders can upload JPEG, PNG, or WebP photos up to 8 MB and UTF-8 TXT, Markdown, CSV, TSV, JSON, JSONL, XML, YAML, and log documents up to 64 KB when file malware scanning is configured. Attachments are scanned before their content reaches the model, temporarily staged in R2, and deleted after processing; extracted document text is retained in conversation history, while image bytes are not. When scanning is unavailable or fails, attachments are refused. A sender needs an owner-managed per-user grant to discover and execute an installed skill or enabled MCP tool; the existing bot-level grant is checked as well.

Manage a sender's tool grants with `GET` or `PUT /v1/bots/{botId}/telegram/users/{telegramUserId}/tool-grants` using `bots:read` or `bots:write`. A `PUT` body contains a `toolRefs` array such as `{ "toolRefs": ["skill:weather.lookup", "mcp:mcp_<server-id>:lookup"] }`. Only already-allowed sender IDs can receive grants, and removing a sender from the allowlist cascades away their grants.

Create a schedule with `POST /v1/bots/{botId}/scheduled-tasks` using `bots:write` and `agent:run`. The JSON body contains `schedule` (`once:<ISO timestamp>` or `daily:HH:mm`), an IANA `timezone`, `prompt`, and an approved `notifyTelegramUserId`. The bot must be published and Telegram-connected. Use collection `GET` to list tasks, task `PATCH` with `{ "status": "paused" }` or `{ "status": "active" }` to pause/resume, task `DELETE` to pause, and owner-only `POST /{taskId}/retry` to requeue a failed run after the bounded automatic retries. A retry may redeliver a Telegram message if the previous attempt succeeded remotely but timed out before local completion. The Durable Object stores schedule metadata and a reference only; task prompts and model output stay in D1.

Review uncertain remote tool calls in the bot's Tool recovery tab, or use `GET /v1/bots/{botId}/tool-executions` with `bots:read`. The endpoint returns tool name, hashed execution key, recovery status, and timestamps; it never returns tool input or result data. To resolve an ambiguous call, send `POST /v1/bots/{botId}/tool-executions/{executionKey}/resolve` with `{ "resolution": "retry" }` or `{ "resolution": "close" }` and `bots:write`. Retry approval permits one replay only when the original request is delivered again with the same execution key. It does not dispatch a new execution from the dashboard. Check the remote service before approving because the original call may already have completed.

Non-streaming model calls retry transient HTTP responses up to `MODEL_RETRY_MAX_ATTEMPTS` (1–3, default 2), waiting `MODEL_RETRY_BACKOFF_MS` milliseconds before the first retry (0–3000, default 250) and doubling subsequent waits. A provider `Retry-After` is honored only up to three seconds. Streaming calls and ambiguous network failures are not retried. Telegram retries only explicit `429` responses; configure `TELEGRAM_RETRY_MAX_ATTEMPTS` (1–3, default 2) and `TELEGRAM_RETRY_MAX_AFTER_SECONDS` (0–3, default 3). Scheduled jobs use `SCHEDULED_TASK_RETRY_MAX_ATTEMPTS` (1–10, default 5), `SCHEDULED_TASK_RETRY_BACKOFF_MS` (0–3600000, default 30000), and `SCHEDULED_TASK_RETRY_MAX_BACKOFF_MS` (0–3600000, default 3600000). Model, HTTP-skill, Telegram, and scheduled-job retry events use the shared sanitized structured logger and exclude prompts, request bodies, credentials, and remote response text. Transient provider errors can still incur a second charge.

## File scanning

Uploaded bot files are stored in R2 and remain quarantined until the configured scanner returns a clean verdict. The scanner is an operator-managed HTTPS gateway, not an antivirus bundled into this Worker. Set `FILE_SCANNER_ENDPOINT` to its full HTTPS URL and `FILE_SCANNER_ALLOWED_ORIGINS` to that exact origin in the chosen Wrangler environment. Store the credential only as a Worker secret, for example `bunx wrangler secret put FILE_SCANNER_TOKEN --env development`. For Bun, use the corresponding private `.env` values. Do not put the token in `wrangler.jsonc` or Git. The root Docker Compose setup now includes an optional Caddy TLS edge for the Bun-hosted ClamAV gateway; it forwards only `POST /internal/file-scan`, keeps the Bun port loopback-bound by default, and never publishes ClamAV's TCP port. See the root README for DNS, certificate, Worker variable, and secret setup.

For self-hosted Bun, an optional direct ClamAV adapter is available instead: set `CLAMAV_HOST=clamav` and enable the Compose profile with `docker compose --profile clamav up --build -d`. It sends bounded `INSTREAM` frames over the private container network and does not publish ClamAV's TCP port. Configure either the Bun ClamAV adapter or the HTTPS scanner gateway, not both. This adapter is not used by Cloudflare Workers.

For each scan, the runtime sends a `POST` with the file bytes as the body, the original `Content-Type`, `x-file-name-encoded` containing the percent-encoded file name, and `Authorization: Bearer <FILE_SCANNER_TOKEN>`. Redirects are rejected. The gateway must return a bounded JSON response such as `{ "verdict": "clean", "scanner": "ClamAV" }` or `{ "verdict": "infected", "scanner": "ClamAV" }`. Errors or malformed responses leave the file in `scan_failed` so an owner can retry after the gateway recovers. Infected files are rejected and removed from R2. The runtime advertises `fileMalwareScanning: false` unless the endpoint, exact-origin allowlist, and secret are all configured; without scanning, file downloads remain blocked and Telegram attachments are refused.

## Environments and local checks

`TELEGRAM_CUSTOMER_REQUESTS_PER_MINUTE` sets the fixed UTC-minute limit for each approved sender on each customer bot. It defaults to 30, accepts values from 1 to 1,000, and suppressed updates are acknowledged silently after update deduplication. Sender identifiers are stored only as deployment-scoped SHA-256 hashes; migration `0030_telegram_customer_rate_limits.sql` adds this usage state to D1 and Bun SQLite.

`NETWORK_REQUESTS_PER_MINUTE` sets a persistent fixed UTC-minute limit shared across app accounts, defaulting to 600 and accepting values from 10 to 10,000. The Worker uses Cloudflare's client IP metadata; Bun uses the socket peer address and does not trust forwarded headers. Both runtimes HMAC the address with the active secret-encryption key before storing the counter, and migration `0031_network_request_limits.sql` stores only the keyed hash. Health endpoints and Telegram webhook traffic bypass this shared limit; invalid Telegram webhook attempts count against it. Configure a corresponding ingress limit at any reverse proxy in front of Bun.

The development Worker is deployed at `https://aihat-bot-factory.work-fdc.workers.dev`; its D1 database has migrations `0001` through `0031` applied. Its R2 bucket, Queue, Telegram master-bot token, webhook secret, factory model secret, and encryption keyring are configured. The active Worker version `cf0bdb63-b158-4ed0-8a2b-ce39137db544` includes public Web Chat, dashboard CSP and Telegram-compatible popup isolation, and the optional HTTPS file-scanner gateway integration. Telegram browser sign-in remains disabled until `TELEGRAM_LOGIN_CLIENT_ID` and the BotFather origin are configured.
